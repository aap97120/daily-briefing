🧠 Data Science Topic of the Day

🎓 Vector Databases & Embedding Search

The memory layer that lets AI agents find the right business entity, document, or signal — fast.

What It Is

A vector database stores data not as rows and columns but as high-dimensional numeric vectors — mathematical representations of meaning. When you embed a piece of text, a company profile, or a product description using a model like OpenAI's text-embedding-ada or a fine-tuned encoder, you get a list of numbers (e.g. 1,536 floats) that captures semantic meaning. Similar things end up close together in this vector space. A vector database (Pinecone, Weaviate, Qdrant, pgvector, Milvus) indexes billions of these vectors and retrieves the nearest neighbours in milliseconds using algorithms like HNSW (Hierarchical Navigable Small World) or IVF (Inverted File Index). This is the core infrastructure behind semantic search, RAG pipelines, recommendation engines, and agentic memory — anywhere you need 'find me things that mean the same thing' rather than 'find me exact keyword matches.'

How It Works

1. EMBEDDING: A transformer encoder converts raw input (text, tabular data serialised as text, images) into a dense vector. The model is trained so that semantically similar inputs produce geometrically close vectors — cosine similarity or dot product measures closeness. 2. INDEXING: Vectors are inserted into the database alongside a payload (metadata: company name, DUNS number, industry, timestamp). HNSW builds a multi-layer graph where each node links to its approximate nearest neighbours — enabling sub-linear search (you skip most of the space). 3. QUERYING: At query time, your search string is embedded with the same model. The database performs Approximate Nearest Neighbour (ANN) search — returning the top-K vectors by similarity score. Metadata filters (e.g. 'only return records where country = US AND revenue > $10M') are applied as pre- or post-filters. 4. HYBRID SEARCH: Most production systems combine dense vector search (semantic) with sparse keyword search (BM25 / TF-IDF) using a technique called Reciprocal Rank Fusion (RRF) — you get the best of exact-match and fuzzy-meaning retrieval simultaneously. 5. RE-RANKING: A cross-encoder re-ranks the top-K candidates with higher accuracy (it sees both query and document together), trading speed for precision at the final step. Key parameters to tune: vector dimension, index type (HNSW vs IVF_FLAT), ef_construction (build-time graph quality), ef_search (query-time recall vs latency trade-off), and number of results K.

When To Use

— Semantic search over large unstructured corpora (sales call transcripts, firmographic descriptions, news articles about companies) — Entity resolution at scale: fuzzy-match an inbound company name/address against 600M records without exact string rules — Agentic memory: give a LangChain/LangGraph agent a persistent store of past interactions, account context, or retrieved facts — Recommendation: 'companies like this one' for look-alike prospecting — RAG pipelines: the retrieval layer that fetches grounding context before an LLM generates an answer — Anomaly detection: flag records whose embedding is far from any known cluster Do NOT use a vector database when: you need exact transactional lookups (use a relational DB), you need aggregations over structured fields (use a data warehouse), or your corpus is small enough that brute-force cosine similarity in NumPy is fast enough (under ~50k vectors).

🎯 Worked Example — D&B Context

PROBLEM: D&B's Prospecting Agent receives a natural-language request from a sales rep — 'Find me mid-market US logistics companies that are expanding their fleet and have healthy payment behaviour.' No structured filter maps cleanly to 'expanding their fleet.' SOLUTION WITH VECTOR SEARCH: 1. CORPUS PREPARATION: D&B serialises each of its 600M+ business records into a short structured narrative: 'Acme Freight LLC. Industry: Trucking & Warehousing. Employees: 420, +18% YoY. Fleet assets: 310 trucks, +22 added Q2 2026. Paydex: 82. Buydex signal: 3 active equipment RFPs detected.' Each narrative is embedded using a fine-tuned B2B encoder and stored in a Pinecone index alongside structured metadata (country, revenue band, Paydex score). 2. QUERY: The rep's natural language request is embedded. A hybrid search runs: dense vector similarity finds companies whose narrative embedding is close to 'fleet expansion + logistics growth' even if those exact words aren't present; a metadata filter constrains to US, revenue $10M–$500M, Paydex ≥ 75. 3. RESULT: Top-20 semantically matched companies are returned in ~80ms, re-ranked by a cross-encoder that weighs recency of Buydex signal. The Prospecting Agent presents them with explainable highlights — 'Ranked #1 because fleet asset growth is in the 94th percentile for this segment and 2 active equipment RFPs were detected this month.' 4. MOAT: This only works because D&B's proprietary Paydex, Buydex, and corporate family tree data is baked into the embedded narratives — a competitor using public web data alone would embed far noisier, less predictive representations. The DUNS number in the metadata payload ensures every retrieved entity resolves cleanly into D&B's entity graph, eliminating duplicates. This is explainability + entity resolution + temporal buying-window signals all delivered through a vector search layer — the AI Decision Intelligence stack in action.
