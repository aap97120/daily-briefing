🧠 Data Science Topic of the Day

🎓 Vector Databases

The memory layer that makes AI agents fast, accurate, and context-aware at scale.

What It Is

A vector database stores data not as rows and columns but as high-dimensional numerical vectors — mathematical representations of meaning. When an AI model (like an embedding model) reads a piece of text, an entity name, or a product description, it converts it into a vector: a list of hundreds or thousands of numbers that encode semantic meaning. A vector database indexes these vectors so you can ask 'find me everything similar to this' in milliseconds across billions of records. Think of it as a search engine that understands meaning rather than just matching keywords. Popular implementations include Pinecone, Weaviate, Qdrant, Chroma, and pgvector (Postgres extension). They are the foundational memory and retrieval layer for RAG pipelines, semantic search, recommendation engines, and agentic AI workflows.

How It Works

1. EMBEDDING: An embedding model (e.g. OpenAI text-embedding-3-large, Cohere embed-v3, or a fine-tuned BERT variant) converts raw data — text, entity names, company descriptions — into a dense vector, e.g. [0.12, -0.87, 0.34, … 1536 dimensions]. Similar items cluster near each other in this high-dimensional space. 2. INDEXING: The database builds a spatial index over all vectors using approximate nearest neighbour (ANN) algorithms. The dominant algorithm family is HNSW (Hierarchical Navigable Small World graphs) — a layered graph structure where each node connects to its nearest neighbours. At query time it traverses the graph top-down, narrowing the search space exponentially. Other options include IVF (Inverted File Index, which clusters vectors into buckets first) and DiskANN for disk-resident datasets too large for RAM. 3. QUERYING: You embed your query using the same model, then ask the DB for the top-K nearest vectors by cosine similarity or Euclidean distance. Cosine similarity is preferred for text because it measures the angle between vectors (semantic direction) independent of magnitude. 4. FILTERING: Most production vector DBs support metadata filtering — e.g. 'find semantically similar companies BUT only in the SaaS vertical with revenue > $10M' — combining vector search with traditional predicate filtering. 5. RETRIEVAL AUGMENTED GENERATION (RAG) LOOP: The retrieved vectors and their payloads are injected as context into an LLM prompt, grounding the model's answer in real, structured facts rather than hallucinated knowledge. This is why vector databases are the critical infrastructure layer beneath every serious enterprise AI deployment.

When To Use

Use a vector database when: (a) you need semantic search — finding conceptually similar items even when exact keywords don't match; (b) you are building a RAG pipeline where an LLM needs to retrieve grounded context before answering; (c) you need entity resolution or deduplication at scale — matching 'International Business Machines Corp' to 'IBM' to 'I.B.M.' without hard-coded rules; (d) you are powering a recommendation engine based on behavioural or content similarity; (e) your agentic AI workflow needs long-term memory that persists across sessions. Do NOT use a vector database as a replacement for a relational or analytical database — they are complements, not substitutes. Best combined with a metadata store (Postgres, DynamoDB) for structured filtering alongside the ANN search.

🎯 Worked Example — D&B Context

D&B ENTITY RESOLUTION & PROSPECTING AGENT — CONCRETE EXAMPLE: D&B has 600M+ business records. A common pain: a sales rep types 'find me companies similar to Salesforce but in the UK mid-market.' Keyword search fails — it returns companies literally mentioning Salesforce. Here is how a vector database solves it end-to-end. STEP 1 — EMBED THE D&B CORPUS: For every D&B business record, concatenate key structured fields into a rich text blob: company name, primary SIC/NAICS description, employee band, revenue band, corporate family tree depth, Paydex score tier, recent Buydex signal category. Run this through an embedding model (e.g. Cohere embed-v3 fine-tuned on B2B entity text). Store the resulting vector alongside the DUNS number as metadata in Pinecone or Qdrant. STEP 2 — QUERY: The Prospecting Agent embeds the rep's natural language query. It also optionally embeds the customer's own existing top accounts as 'positive exemplar' vectors and averages them into a target vector (a classic technique called query expansion by centroid). STEP 3 — FILTERED ANN SEARCH: Execute a top-500 nearest-neighbour search, but apply metadata filters: country_code = 'GB', employee_band IN ['50-249','250-999'], Paydex_tier >= 'Good'. This combines semantic similarity with hard business constraints — something a keyword search or SQL LIKE query cannot do. STEP 4 — BUYDEX RE-RANKING: The raw ANN results are re-ranked by Buydex buying-intent signals — companies showing active purchase signals rise to the top. This is a two-stage retrieval + ranking pipeline, identical in architecture to how Google's search ranking works. STEP 5 — LLM SYNTHESIS: The top 10 results (with their D&B attributes) are passed to an LLM that writes a personalised account brief for each, explaining WHY each company resembles the rep's best customers. The explainability is inherent — the retrieved vectors and their metadata ARE the ground truth, so the agent can cite 'similar SIC code, comparable Paydex trajectory, same employee band' rather than hallucinating reasons. WHY THIS IS STRATEGICALLY IMPORTANT: This architecture makes DUNS number the anchor key in every vector payload — so entity resolution is baked into the retrieval layer, not bolted on afterwards. Every AI agent that queries this system gets D&B's 600M record corpus as its semantic memory. That is the 'AI Decision Intelligence' moat made concrete: not just a data feed but the foundational retrieval substrate of agentic workflows.
