🧠 Data Science Topic of the Day

🎓 Feature Stores

The shared memory layer that stops your ML teams from recomputing the same features twelve different ways.

What It Is

A feature store is a centralised data system that sits between your raw data pipelines and your ML models. It has two jobs: (1) compute and store feature values consistently so every model — whether in training or live inference — sees the same numbers, and (2) serve those features at low latency when an agent or model needs a prediction right now. Think of it as a versioned, queryable library of 'facts about entities' — customers, companies, products — that any model can borrow without rebuilding from scratch. In D&B's world, an entity is almost always a business identified by a DUNS number, making feature stores a natural complement to entity resolution.

How It Works

A feature store has four moving parts: 1. **Feature Pipeline (Offline):** Batch jobs (Spark, dbt, Flink) read raw data and compute features — e.g. 'rolling 90-day Paydex trend for DUNS 123456789'. Results land in an offline store (a data warehouse or Delta Lake table) used for model training. 2. **Online Store:** A low-latency key-value database (Redis, DynamoDB, Bigtable) holds the *latest* feature values per entity. At inference time, a model requests features by entity key and gets a response in <10ms. 3. **Feature Registry:** A catalogue that stores feature definitions, owners, data lineage, and versions. This is what prevents two teams computing 'days_since_last_payment' differently. 4. **Point-in-Time Correctness:** When generating a training dataset, the feature store reconstructs what feature values *looked like at the moment a label was created* — not their current values. This eliminates a subtle but devastating bug called training-serving skew, where a model trains on future-leaked data and fails in production. Popular open-source options: Feast. Managed options: Tecton, Hopsworks, Databricks Feature Store, Vertex AI Feature Store.

When To Use

Use a feature store when: - **Multiple models share features:** If your propensity-to-buy model and your churn model both need 'company headcount growth rate', compute it once. - **Online + offline parity matters:** Any real-time scoring scenario (a sales agent asking 'is this account ready to buy right now?') where training-serving skew would silently corrupt predictions. - **Feature reuse across teams:** When a data science team in APAC shouldn't have to reverse-engineer what the Americas team built. - **Regulated or explainable AI contexts:** The registry gives you an audit trail — what feature definition was model v2.3 trained on, and has it drifted? Do NOT over-engineer with a feature store if you have one model, one team, and purely batch predictions. The overhead isn't worth it at that scale.

🎯 Worked Example — D&B Context

**D&B Account Expansion Agent — 'Buydex Signal Readiness' Scoring** Scenario: D&B's Account Expansion agent archetype needs to rank existing customers by their likelihood to expand into a new product (e.g. upgrading from basic firmographics to the full Buydex intent signal suite). The agent runs in Salesforce Agentforce and must return a ranked list in real time when a rep opens an account page. **Without a feature store:** Three separate data science squads each compute their own version of 'Paydex momentum', 'corporate family tree expansion rate', and 'recent employee growth'. Each squad's definition drifts. The training dataset leaks future Paydex values. The live Salesforce call hits a slow SQL query and times out. **With a feature store (Tecton + Redis):** - An offline Spark pipeline runs nightly, computing ~40 DUNS-level features: rolling Paydex z-score (30/60/90d), corporate family tree new subsidiary additions (L12M), firmographic volatility index, prior product adoption breadth, days since last CRM interaction. - These land in the offline store for model retraining and in Redis for live serving. - Point-in-time correctness ensures the training labels (expansion event date) align to feature snapshots *before* the expansion — no leakage. - The Feature Registry records that 'paydex_zscore_90d_v2' replaced 'paydex_zscore_90d_v1' on 2026-03-15, with the change documented. - When the Agentforce expansion agent fires, it calls the feature store with a DUNS key, gets 40 features back in 8ms, scores the model, and returns a ranked recommendation with SHAP-based plain-English rationale ('This account's Paydex score improved 1.8 standard deviations over 90 days while adding 3 subsidiaries — high readiness signal.'). - **Result:** Model retraining time drops 60% (no feature recompute), three teams share the same definitions, and the live agent response is well within Salesforce's UI latency budget.
