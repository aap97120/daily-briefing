🧠 Data Science Topic of the Day

🎓 Apache Spark — Distributed Data Processing at Scale

When your data is too big for one machine, Spark turns a cluster into a single, fast engine.

What It Is

Apache Spark is an open-source, in-memory distributed computing framework designed to process massive datasets across clusters of machines in parallel. Unlike its predecessor Hadoop MapReduce — which wrote intermediate results to disk after every step — Spark keeps data in memory across computation stages, making iterative workloads (ML training, graph analytics, streaming) orders of magnitude faster. It exposes a unified API across four libraries: Spark SQL (structured data), MLlib (machine learning), GraphX (graph processing), and Spark Streaming / Structured Streaming (real-time data). The core abstraction is the Resilient Distributed Dataset (RDD) — a fault-tolerant, partitioned collection of records spread across nodes — though most modern Spark work uses the higher-level DataFrame and Dataset APIs, which let the Catalyst query optimizer and Tungsten execution engine squeeze out additional performance automatically.

How It Works

1. CLUSTER ARCHITECTURE: A Spark job runs on a Driver node (your program's main process) plus N Executor nodes. The Driver builds a Directed Acyclic Graph (DAG) of transformations; the Cluster Manager (YARN, Kubernetes, or Spark Standalone) allocates executors. 2. LAZY EVALUATION: Transformations like filter(), join(), and groupBy() are 'lazy' — they build a logical plan but do nothing until an Action (count(), write(), collect()) is called. This allows Catalyst to reorder, push down, and fuse operations before a single byte moves. 3. PARTITIONING & SHUFFLES: Data is split into partitions (think: shards). Most transformations are partition-local and fast. Aggregations and joins that require data from multiple partitions trigger a 'shuffle' — the most expensive operation — redistributing data across the network. Minimising shuffles (via broadcast joins for small tables, partitioning on join keys, bucketing) is the primary tuning lever. 4. IN-MEMORY CACHING: .cache() or .persist() materialises an intermediate DataFrame in executor memory so downstream steps reuse it without recomputation — critical for iterative ML or repeated dashboard queries on the same base table. 5. STRUCTURED STREAMING: Spark processes live streams (Kafka, Kinesis) as a continuous series of micro-batch DataFrames, using the same SQL/DataFrame API as batch — one codebase for both modes. 6. DELTA LAKE INTEGRATION: Most production Spark deployments now sit on Delta Lake (open-source ACID table format), giving transactional writes, time-travel queries, and schema enforcement on top of cheap object storage (S3, ADLS).

When To Use

Use Spark when: (a) data volume exceeds what fits comfortably in a single-node tool like pandas or dbt — typically 10 GB+ per job; (b) you need to join multiple large tables (e.g., entity resolution at 600M+ record scale); (c) ML feature pipelines must process billions of rows before training; (d) real-time scoring or streaming enrichment is required; (e) you need repeatable, versioned large-scale ETL that feeds a feature store or data warehouse. Do NOT use Spark for: small datasets (the cluster overhead kills you), low-latency sub-10ms API calls (use a serving layer instead), or highly interactive exploratory analysis on modest data (pandas/DuckDB wins there).

🎯 Worked Example — D&B Context

D&B's entity resolution pipeline must match and deduplicate 600M+ business records arriving daily from thousands of data contributors against the canonical DUNS registry. In Spark: Step 1 — Ingest raw contributor files from S3 into a Delta Lake landing zone via Structured Streaming; each file partition maps to a Spark partition. Step 2 — Normalise company names, addresses, and phone numbers using Spark SQL UDFs (strip legal suffixes, standardise country codes). Step 3 — Blocking: partition the DataFrame by first-3-chars of company name AND country code to reduce the comparison space from O(n²) to manageable candidate pairs — a shuffle-once operation. Step 4 — Within each block, broadcast a small lookup table of DUNS anchor records and compute fuzzy match scores (Jaro-Winkler + address similarity) using a vectorised pandas UDF on each executor. Step 5 — Aggregate scores, apply the Paydex-weighted confidence threshold, and write resolved DUNS assignments back to Delta Lake with full lineage (Delta time-travel lets you audit any prior resolution). Step 6 — Downstream, a feature store job reads the resolved Delta table to compute Buydex buying-signal features at account level — these feed directly into the Prospecting Agent archetype. The whole pipeline runs in ~40 minutes on a 200-node cluster rather than days on a single machine, and Delta ACID guarantees mean a failed mid-run never corrupts the production entity graph.
