🧠 Data Science Topic of the Day

🎓 Knowledge Graphs

The structured backbone that turns disconnected facts into navigable, reasoned intelligence

What It Is

A knowledge graph is a network of real-world entities — companies, people, products, relationships — stored as nodes and edges, where each edge carries a typed, directional meaning. Unlike a flat table or even a document store, a knowledge graph captures *how* things relate: Acme Corp *is a subsidiary of* GlobalHoldings Inc, which *operates in* the Chemicals sector, which *is regulated by* the EPA. D&B's corporate family tree and DUNS entity graph are, at their core, knowledge graphs. The formal substrate is typically a triple store (Subject → Predicate → Object) queryable via SPARQL or a property graph (Neo4j-style) queryable via Cypher. The power is not just storage — it is multi-hop traversal: answer questions that require chaining three, five, or ten relationships that no single table could express.

How It Works

**1. Entity and Relation Extraction.** Raw data (filings, web text, CRM records) is parsed using NLP or rule-based extractors to identify entities (org names, addresses, roles) and the typed relations between them. **2. Entity Resolution / Deduplication.** Incoming entities are matched to canonical nodes — this is where DUNS-style resolution earns its value. Two records for 'GE Capital Corp' and 'General Electric Capital' must collapse to one node before any graph traversal is meaningful. **3. Schema / Ontology Definition.** An ontology defines what node types exist (Company, Person, Address, Industry, Product) and which edge types are legal (subsidiary_of, headquartered_in, primary_contact_of). Without a schema the graph becomes an unstructured mess. **4. Graph Storage & Indexing.** Property graphs (Neo4j, Amazon Neptune, TigerGraph) store nodes and edges with attached key-value properties. Triple stores (Apache Jena, Stardog) follow W3C RDF standards. Both support index structures that make neighbor lookups O(1) regardless of graph size. **5. Multi-hop Querying.** A Cypher query like `MATCH (a:Company)-[:SUBSIDIARY_OF*1..5]->(p:Company {name:'GlobalHoldings'}) RETURN a` finds all subsidiaries up to five hops deep — impossible in standard SQL without recursive CTEs and painful at scale. **6. Graph Embeddings (optional).** Algorithms like TransE, RotatE, or GraphSAGE learn low-dimensional vector representations of nodes. These embeddings encode structural position, enabling downstream ML tasks: link prediction (will this company acquire that one?), anomaly detection (unusual ownership loops), and semantic similarity between entities never explicitly connected. **7. Integration with LLMs / Agents.** Modern architectures combine knowledge graphs with LLMs via GraphRAG — instead of stuffing raw text into a retrieval index, you retrieve *graph subgraphs* as context. The LLM gets structured, fact-checked relationships rather than noisy prose, dramatically reducing hallucination on entity-specific questions.

When To Use

Use a knowledge graph when: (1) your domain has rich, heterogeneous relationships that matter as much as attributes — ownership chains, supply networks, org hierarchies; (2) you need multi-hop reasoning that SQL joins cannot express cleanly; (3) you are building an AI agent that must navigate relationships dynamically rather than retrieve flat rows; (4) entity resolution is a first-class problem — you need one canonical node per real-world thing; (5) explainability is non-negotiable — a graph path *is* the explanation (Company A is risky because it is a subsidiary of Company B which defaulted). Avoid when data is genuinely tabular with shallow relationships and query patterns are known and fixed — a relational DB will outperform on raw throughput.

🎯 Worked Example — D&B Context

**D&B Prospecting Agent — 'Who else is hiding in this account?'** A sales rep closes a deal with Meridian Logistics LLC. The Prospecting Agent needs to find every related entity that is a warm expansion target but is not yet in the CRM. **Step 1 — Anchor on DUNS.** Entity resolution maps 'Meridian Logistics LLC' to DUNS #123456789, the canonical node in D&B's graph. **Step 2 — Traverse the corporate family tree.** A multi-hop Cypher query walks the `SUBSIDIARY_OF` and `BRANCH_OF` edges up to the global ultimate parent (GUP) — say, Meridian Group PLC — then back down to all 47 sibling and child entities globally. **Step 3 — Enrich nodes.** Each discovered entity node carries Paydex score, Buydex intent signal, employee count, and D&B industry classification as node properties. **Step 4 — Filter and rank.** The agent filters for nodes where Buydex shows active intent in the rep's solution category AND Paydex ≥ 70 (creditworthy). It surfaces 6 whitespace targets across 3 countries — none in the CRM. **Step 5 — Explainable output.** The agent returns not just a list but the traversal path: 'Meridian Nordic AB is a subsidiary (2 hops) of the same GUP as your closed account, shows intent for supply-chain software, and has a Paydex of 82.' The *graph path is the explanation* — no black box, full auditability. This is exactly D&B's structural moat: 600M+ records already organized as a knowledge graph. No competitor builds this from scratch in a sprint. The agent is better *because* the graph is deeper.
