🧠 Data Science Topic of the Day

🎓 dbt (data build tool) — Analytics Engineering in Practice

Version-controlled, tested, documented SQL pipelines that turn raw data into trusted analytical assets — the connective tissue between raw business records and every model D&B builds.

What It Is

dbt is an open-source transformation framework that lets data and analytics engineers write modular SQL SELECT statements (called 'models') and dbt handles the rest: materializing them as tables or views, managing dependencies between them, running data quality tests, and auto-generating documentation. It does not extract or load data — it sits in the T of ELT. The key insight is treating SQL transformations like software: every model lives in version control (Git), has unit-testable assertions, and is documented in YAML alongside the code. dbt Cloud is the managed SaaS layer; dbt Core is the open-source CLI. Together they have made 'analytics engineering' a recognized discipline sitting between data engineering and data science.

How It Works

1. MODELS — Each model is a .sql file containing a single SELECT. dbt compiles it into CREATE TABLE AS or CREATE VIEW AS. Models reference each other with the ref() macro (e.g. FROM {{ ref('stg_accounts') }}), which dbt resolves into a DAG (directed acyclic graph). 2. MATERIALIZATIONS — Four types: view (default, rebuilt every query), table (rebuilt every run), incremental (only processes new/changed rows using a filter, critical for large datasets like 600M D&B records), ephemeral (CTE injected inline, never stored). 3. SOURCES — Raw tables are declared in YAML as 'sources', giving them freshness checks (warn if not updated in N hours) and a clean boundary between ingestion and transformation. 4. TESTS — Two types: generic (not_null, unique, accepted_values, relationships — declared in YAML in one line) and singular (custom SQL that should return zero rows if data is clean). Tests run with 'dbt test' and block promotion if they fail. 5. MACROS — Jinja-templated SQL functions that eliminate duplication, e.g. a macro that stamps every model with a row_hash, loaded_at, and source_system column. 6. SEEDS — Small CSV files (lookup tables, mapping files) version-controlled and loaded with 'dbt seed'. 7. EXPOSURES & METRICS — Exposures declare downstream consumers (dashboards, ML models) so lineage extends end-to-end. The dbt Semantic Layer lets you define metrics once (e.g. 'pipeline_coverage_ratio') so every tool queries the same definition. 8. LINEAGE & DOCS — 'dbt docs generate' produces an interactive DAG browser showing column-level lineage from raw source to final mart. This is lineage as a first-class artifact, not an afterthought.

When To Use

Use dbt when: (a) transformation logic is primarily SQL and lives in a cloud data warehouse (Snowflake, BigQuery, Databricks, Redshift); (b) multiple analysts are writing overlapping SQL and there is no single source of truth; (c) you need auditable, testable pipelines for regulated or high-stakes data (credit risk, compliance); (d) you want column-level lineage for governance or model explainability traceability; (e) incremental processing of very large tables (hundreds of millions of rows) where full refreshes are cost-prohibitive. Do NOT use dbt as a replacement for Spark when transformations require non-SQL logic, complex UDFs, or streaming. It pairs naturally with Airflow or Prefect for orchestration — dbt handles the what-to-transform, the orchestrator handles when.

🎯 Worked Example — D&B Context

D&B ingests raw Paydex payment records, firmographic snapshots, and intent signals from third-party providers nightly into Snowflake. Without dbt, 12 different analysts have 12 slightly different definitions of 'active company' and 'high-propensity account.' With dbt: (1) A 'staging' layer (stg_paydex, stg_firmographics, stg_intent) does light cleaning and casts types — one canonical definition per source. Generic tests assert DUNS number is never null and is unique per snapshot date. A freshness check fires a Slack alert if stg_paydex hasn't refreshed in 26 hours. (2) An 'intermediate' layer joins entities using DUNS as the spine — the ref() DAG makes the dependency explicit and visible. An incremental model processes only yesterday's new payment observations rather than reprocessing 600M rows. (3) A 'mart' layer produces mart_account_intelligence: one row per DUNS per week with Paydex score, Buydex propensity score, corporate family tree depth, days-since-last-intent-signal, and a composite buying_window_score. A singular test asserts buying_window_score is always between 0 and 100. (4) The dbt Semantic Layer exposes a 'pipeline_at_risk_accounts' metric (Paydex < 50 AND open_opportunity = TRUE) that Salesforce, Tableau, and the Pipeline Risk Agent all query from one definition — no metric drift. (5) 'dbt docs generate' gives the ML team full column-level lineage from raw payment file → buying_window_score, satisfying the Explainability First requirement when a prospect challenges why they were flagged as high-risk. The entire pipeline is in Git, peer-reviewed via pull request, and any analyst can trace exactly which raw fields drove a model score.
