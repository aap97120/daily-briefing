🧠 Data Science Topic of the Day

🎓 Retrieval-Augmented Generation (RAG)

Give your LLM a memory it can actually trust — by wiring it to verified, up-to-date external knowledge at query time.

What It Is

RAG is an architecture that stops a large language model from relying solely on what it memorised during training. Instead, at inference time, it retrieves a small, relevant set of documents from an external store — a vector database, a knowledge base, or a structured data layer — and feeds those documents into the prompt as grounded context before the model generates its response. The result is an answer that is both fluent (LLM strength) and factually anchored (retrieval strength). For D&B, RAG is the architectural pattern that makes 'AI Decision Intelligence' real: the agent doesn't hallucinate a company's credit risk or ownership structure — it retrieves the live Paydex score, the corporate family tree, and the Buydex signal, then reasons over verified ground truth.

How It Works

1. EMBED THE CORPUS — Source documents (D&B business records, news, filings, internal CRM notes) are chunked and converted into dense vector embeddings using an encoder model (e.g. OpenAI text-embedding-3-large, Cohere embed-v3, or a fine-tuned bi-encoder). These vectors are indexed in a vector database such as Pinecone, Weaviate, pgvector, or Chroma. 2. RETRIEVE AT QUERY TIME — The user's question is embedded with the same encoder. A nearest-neighbour search (typically approximate, via HNSW or IVF) finds the top-k most semantically similar chunks. Optional hybrid search combines dense vector similarity with BM25 sparse keyword matching to handle exact entity names and codes reliably — critical for DUNS numbers and SIC codes. 3. RERANK — A cross-encoder reranker (e.g. Cohere Rerank, BGE-reranker) scores each retrieved chunk against the query more precisely. The top 3–5 chunks survive into the prompt. This two-stage retrieve-then-rerank pattern keeps latency low while maximising relevance. 4. AUGMENT THE PROMPT — Retrieved chunks are injected into the LLM prompt as 'context'. A system instruction tells the model: reason only from the provided context; if the answer isn't there, say so. This is the explainability guardrail — the model is forced to cite its sources. 5. GENERATE — The LLM produces a grounded, coherent response. In an agentic workflow (LangChain, LangGraph, Agentforce) the RAG step is just one tool the orchestrator can call; other tools handle calculation, API calls, or writing back to CRM. 6. EVALUATE — RAG quality is measured on three axes: Context Recall (did retrieval surface the right chunks?), Context Precision (were the retrieved chunks all relevant, no noise?), and Answer Faithfulness (did the LLM stay within what the context says?). Frameworks like RAGAS and TruLens automate this evaluation loop.

When To Use

Use RAG when: (a) your knowledge base changes faster than you can retrain — live business data, daily Paydex updates, breaking M&A news; (b) you need the model to cite its sources so a sales rep or risk analyst can verify the claim; (c) fine-tuning is too expensive or the corpus is too large to inject wholesale into context; (d) you need to respect data boundaries — retrieve only the records a user is authorised to see, enforcing row-level security at the retrieval layer rather than the generation layer. Do NOT use vanilla RAG when: the question requires multi-hop reasoning across many documents simultaneously (consider GraphRAG or agentic tool-use instead), or when the answer requires precise arithmetic over structured data (route that to SQL/code execution, not free-text retrieval).

🎯 Worked Example — D&B Context

SCENARIO — D&B Prospecting Agent with Verified Ground Truth. A sales rep at a mid-market bank types: 'Find me manufacturing companies in the Ohio Valley with 50–200 employees, a Paydex above 75, and a recent equipment purchase signal — and tell me why each one is a good prospect right now.' Step 1 — Entity & Filter Layer: The agent resolves 'Ohio Valley manufacturing' against D&B's 600M record graph using SIC codes 2000–3999 and geographic bounding. This produces ~1,400 candidate DUNS entities. Step 2 — Structured Retrieval: Paydex, Buydex (equipment category intent), employee count, and corporate family tree flags are pulled via D&B's API for those 1,400 entities. The 312 that pass the numeric filters proceed. Step 3 — RAG over Unstructured Signals: For each of the top 20 shortlisted companies, the orchestrator fires a RAG query against a vector index of recent news, trade press, and public filings. Query embedding: 'Ohio Valley manufacturer capital equipment investment expansion 2025-2026.' Top-k chunks retrieved, reranked, injected as context. Step 4 — Generation with Citations: The LLM writes a one-paragraph prospect brief per company — 'Acme Stamping (DUNS 12-345-6789): Paydex 81, Buydex signals indicate lathe/press procurement intent in Q2 2026. Recent news [source: Cleveland Business Journal, retrieved chunk] references a plant expansion in Youngstown. Recommended talking point: equipment financing for the new line.' The rep sees exactly where every claim came from. Step 5 — Temporal Freshness: Because retrieval happens at query time, the brief reflects today's Paydex, not a six-month-old model weight. This is the 'buying window' temporal analytics concept operationalised — the agent surfaces the prospect at the moment the signal is live, not after it has decayed. Result: The Prospecting Agent archetype delivers a ranked, explainable, source-cited pipeline list in under 30 seconds. No hallucinated revenue figures. No stale credit scores. Ground truth, by design.
