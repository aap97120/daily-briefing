🧠 Data Science Topic of the Day

🎓 dbt (data build tool) — Transforming Raw Data into Trusted Analytics

SQL-first data transformation that brings software engineering discipline — version control, testing, documentation — to the analytics layer.

What It Is

dbt (data build tool) is an open-source transformation framework that lets analytics engineers write modular SQL SELECT statements ('models') and have dbt handle the materialisation, dependency resolution, testing, and documentation automatically. It sits between your raw data warehouse (Snowflake, BigQuery, Databricks, Redshift) and your downstream consumers — BI tools, ML pipelines, AI agents. The core philosophy is 'EL + T': someone else loads raw data into the warehouse; dbt owns the Transform. Every model is a plain .sql file, every transformation is auditable and version-controlled in Git, and every output can be tested with assertions. The result is a governed, trustworthy analytics layer — exactly what AI agents and ML models need as their ground truth.

How It Works

1. MODELS: Each .sql file is a model — a SELECT query that dbt compiles into a CREATE TABLE or CREATE VIEW statement. Models reference each other via the ref() macro (e.g. FROM {{ ref('stg_company_firmographics') }}), which builds a Directed Acyclic Graph (DAG) of dependencies automatically. 2. DAG & LINEAGE: dbt resolves the DAG and executes models in the correct order. You visualise the full lineage — raw source → staging → intermediate → mart — in the dbt Docs UI. This makes data provenance auditable. 3. MATERIALISATION STRATEGIES: models can be views (cheap, always fresh), tables (full rebuild each run), incremental (append/upsert only new rows — critical for 600M+ record datasets), or ephemeral (CTEs, no storage). Incremental models are the workhorse for large-scale entity data. 4. TESTS: dbt ships built-in schema tests — not_null, unique, accepted_values, relationships — declared in YAML. Custom tests can encode business logic (e.g. 'Paydex score must be between 1 and 100'). Tests run after each build and block promotion if they fail. 5. SOURCES & FRESHNESS: Raw tables are declared as sources with freshness SLAs. dbt source freshness checks alert you if upstream data stops arriving — catching pipeline failures before downstream models silently propagate stale data. 6. MACROS & JINJA: dbt uses Jinja templating, allowing reusable SQL macros — parameterised logic you call like functions. A single 'clean_phone_number' macro applied consistently across all staging models prevents divergent cleaning logic. 7. DOCUMENTATION: Every model and column can have a description in YAML. dbt generates a searchable, interactive data catalogue automatically — the semantic layer for human and agent consumers to understand what each field means.

When To Use

Use dbt when: (a) your raw warehouse data needs repeated, auditable transformation before ML or AI consumption — staging, joining, aggregating, deduplicating; (b) multiple teams or agents query the same underlying data and you need a single source of truth rather than bespoke per-notebook SQL; (c) data quality assertions must be enforced systematically, not just hoped for; (d) you are building a feature store layer on top of a data warehouse and want lineage traceability from raw event to ML feature; (e) you need incremental processing at scale — refreshing only new/changed records rather than rebuilding 600M rows every run. Avoid dbt for real-time streaming transformations (use Spark Structured Streaming or Flink instead) or compute-heavy Python transformations that cannot be expressed in SQL.

🎯 Worked Example — D&B Context

D&B Context — Building the 'Account Intelligence Mart' for Agentforce and Copilot Agents. Raw inputs in Snowflake: (1) D&B entity master (DUNS, legal name, corporate family tree, SIC codes), (2) Paydex and Buydex scores (monthly snapshots), (3) CRM opportunity data (Salesforce export), (4) web intent signals (third-party feed). Step 1 — Staging models: stg_entity_master.sql cleans and casts raw entity fields; stg_paydex_history.sql deduplicates monthly score rows and enforces not_null and range tests (Paydex 1–100). Step 2 — Intermediate models: int_corporate_family.sql uses a recursive CTE to flatten parent–subsidiary trees to a single 'ultimate parent DUNS' per entity. int_buying_window.sql joins Buydex trend data with opportunity close dates to calculate 'months_to_likely_purchase' per account — the temporal analytics signal. Step 3 — Mart model: mart_account_intelligence.sql is the single wide table exposed to all agents. It joins entity firmographics, current Paydex, buying window score, open pipeline value, and subsidiary count. Materialised as an incremental table — only accounts with changed Paydex or new intent signals are reprocessed each day. dbt Tests enforce: DUNS uniqueness, Paydex not_null, relationship integrity back to entity master. The Prospecting Agent and Account Expansion Agent both query mart_account_intelligence via a vector DB or direct SQL tool call — and because every column has a dbt YAML description, the agent's LLM context knows exactly what 'buydex_percentile_rank' means without hallucinating. Result: a governed, tested, lineage-documented ground truth layer that makes every downstream AI agent more accurate and explainable — D&B's 'trusted data layer' strategy implemented in code.
