🧠 Data Science Topic of the Day

🎓 LangGraph — Stateful Agent Workflow Orchestration

Move beyond single-shot LLM calls: build agents that plan, loop, branch, and remember — with full control over every step.

What It Is

LangGraph is a graph-based orchestration framework built on top of LangChain that lets you define AI agent workflows as directed graphs — where nodes are actions (LLM calls, tool invocations, data lookups) and edges are the transitions between them, including conditional branches and cycles. Unlike a simple chain that runs once top-to-bottom, LangGraph supports stateful, multi-step agents that can loop, backtrack, pause for human approval, or spawn parallel sub-tasks. Each graph execution carries a persistent 'state' object — a shared memory that every node reads from and writes to — so the agent always knows what it has done, what it found, and what to do next. It is the practical engine behind most serious production agentic systems in 2025–2026, and it maps directly onto the six D&B agent archetypes (Prospecting, Account Intelligence, Pipeline Risk, Territory Planning, Account Expansion, Fleet & Asset).

How It Works

1. DEFINE STATE: Declare a typed Python dataclass (or TypedDict) that holds everything the agent needs to track — e.g., target_company, duns_number, enrichment_results, risk_flags, next_action. 2. BUILD NODES: Write Python functions — each is a node. A node receives the current state, does one unit of work (call a D&B API, run an LLM prompt, query a vector DB), and returns a dict of state updates. Nodes are pure and testable in isolation. 3. WIRE EDGES: Connect nodes with edges. Unconditional edges always proceed to the next node. Conditional edges call a router function that inspects state and returns the name of the next node — enabling branching (e.g., 'if risk_score > 70 → escalate, else → continue'). 4. ADD CYCLES: Unlike DAG frameworks, LangGraph allows edges that loop back — enabling a ReAct-style think→act→observe loop that runs until a termination condition (max iterations, confidence threshold, user approval). 5. CHECKPOINTING: LangGraph integrates with persistent backends (SQLite, Postgres, Redis) to save state after every node. This means an agent can be interrupted, resumed, or replayed — critical for long-running sales workflows that span hours or days. 6. HUMAN-IN-THE-LOOP: A special 'interrupt' mechanism lets you pause graph execution at any node, surface the current state to a human for review or correction, then resume — without losing context. 7. PARALLEL BRANCHES: The Send API lets one node fan out to multiple parallel sub-graphs (e.g., enrich 50 prospect accounts simultaneously), then a reducer aggregates the results back into a single state. Key abstractions: StateGraph (the graph object), CompiledGraph (the runnable), MemorySaver (checkpointer), Command (return type that controls routing), and the interrupt() primitive.

When To Use

Use LangGraph when your agent needs MORE than one round-trip to an LLM — specifically when: (a) the agent must decide what tool to call next based on what it just learned (dynamic planning); (b) outputs must be validated and retried if they fail a quality check; (c) multiple parallel enrichment tasks need to run and then be reconciled; (d) a human must review or approve before the agent proceeds; (e) the workflow is long-running and must survive restarts. Avoid it for single-step prompts, pure RAG lookups, or batch ETL — those do not need graph state. Sweet spot: 3–15 node graphs where control flow is non-trivial but not so complex that it becomes unmaintainable.

🎯 Worked Example — D&B Context

SCENARIO — D&B Pipeline Risk & Revenue Protection Agent. Trigger: A Salesforce opportunity crosses $500K and moves to 'Negotiation' stage. LangGraph kicks off automatically. STATE: { account_name, duns_number, opportunity_value, paydex_score, derogatory_flags, corporate_parent, risk_verdict, recommended_action } NODE 1 — Entity Resolution: Takes the account name from Salesforce, calls D&B DUNS lookup API, writes verified duns_number and corporate_parent to state. If no match found, routes to a 'manual review' node. If matched, proceeds. NODE 2 — Financial Risk Enrichment: Calls D&B Finance & Risk API with duns_number. Pulls Paydex score, days-beyond-terms, bankruptcy indicators, and trade payment trends. Writes to state. NODE 3 — Conditional Router: Inspects paydex_score. If ≥ 80 → route to 'Green Light' node. If 60–79 → route to 'Mitigation' node. If < 60 → route to 'Escalate' node. NODE 4a (Green Light): LLM generates a short 'low risk' memo for the AE. Updates Salesforce opportunity field. Graph ends. NODE 4b (Mitigation): LLM drafts a list of deal structure options (shorter payment terms, partial upfront, credit insurance) referencing the specific Paydex and derogatory data. Writes to state. → INTERRUPT: Pauses and surfaces memo to sales manager for approval. → On approval: pushes recommendations into Salesforce Chatter and emails the AE. NODE 4c (Escalate): Calls the corporate family tree API to check if the parent entity is healthier — if yes, re-routes to suggest invoicing the parent. If parent is also distressed, escalates to CFO review queue with full evidence package. RESULT: Every large deal gets a consistent, auditable, explainable risk verdict — grounded in D&B's proprietary Paydex and entity data — before the contract is signed. The graph's checkpointed state means the full reasoning chain is logged for compliance. This is 'Explainability First' in practice: every risk flag cites a specific D&B data point, not a black-box model score.
