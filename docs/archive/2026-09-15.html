🧠 Data Science Topic of the Day

🎓 dbt (data build tool) — Transforming Raw Data into Reliable Analytics

SQL-first data transformation with software engineering best practices baked in — version control, testing, and documentation for every model.

What It Is

dbt (data build tool) is an open-source transformation framework that lets data engineers and analysts write modular SQL SELECT statements — called 'models' — and then dbt handles compiling, running, testing, and documenting them in your data warehouse. It sits in the 'T' of ELT (Extract, Load, Transform), meaning raw data is loaded into the warehouse first, and dbt transforms it in place. It brings software engineering discipline — version control via Git, unit tests, CI/CD pipelines, and auto-generated data lineage documentation — to what was previously ad hoc SQL scripting. There are two editions: dbt Core (open-source CLI) and dbt Cloud (managed SaaS with a scheduler, IDE, and observability layer).

How It Works

1. MODELS: Each model is a single .sql file containing one SELECT statement. dbt materialises it as a table or view in your warehouse (Snowflake, BigQuery, Redshift, Databricks, etc.). Models reference each other with a {{ ref('model_name') }} macro, which lets dbt build a Directed Acyclic Graph (DAG) of all dependencies automatically. 2. DAG EXECUTION: When you run 'dbt run', dbt resolves the DAG, compiles Jinja-templated SQL into plain SQL, and executes models in the correct dependency order — parallelising where it safely can. 3. TESTING: Two test types exist. (a) Generic tests — built-in assertions like not_null, unique, accepted_values, and relationships — declared in a YAML file alongside each model. (b) Singular tests — custom SQL files that return rows only when a test fails. Tests run via 'dbt test'. 4. SOURCES & STAGING LAYER: Raw tables in the warehouse are declared as 'sources' in YAML. A thin 'staging' model layer renames, casts, and cleans each source table exactly once, giving every downstream model a single clean starting point. 5. MACROS & JINJA: dbt uses Jinja templating inside SQL, enabling reusable logic (macros), environment-aware logic (dev vs. prod schemas), and dynamic SQL generation — without needing a Python script. 6. DOCUMENTATION & LINEAGE: 'dbt docs generate' creates a static website showing every model's description, column definitions, test results, and an interactive DAG lineage graph. This is auto-updated on every run. 7. SEEDS & SNAPSHOTS: Seeds load small static CSV files (e.g. country code lookups) into the warehouse as tables. Snapshots implement Slowly Changing Dimension (SCD Type 2) logic — capturing row-level history as source records change over time.

When To Use

Use dbt when: (1) Your team writes SQL transforms scattered across stored procedures, one-off scripts, or BI tool calculated fields — dbt consolidates and versions all of it. (2) You need auditable, tested data pipelines — every column assertion is codified and runs on a schedule. (3) You want non-engineers (analysts) to contribute to the data pipeline safely via Pull Requests rather than touching production directly. (4) You are building a semantic/metrics layer — dbt's Metrics API lets you define company-wide KPI definitions (e.g. 'ARR', 'churn rate') once, so every downstream tool queries the same number. (5) You need full lineage for regulatory or data governance reasons — the DAG graph shows exactly which raw source feeds which dashboard. Avoid dbt for heavy Python-native transforms (use Spark/pandas for ML feature engineering), real-time streaming (dbt is batch-oriented), or when your data volume makes in-warehouse compute prohibitively expensive.

🎯 Worked Example — D&B Context

D&B Data Products — Temporal Entity Resolution Pipeline Scenario: D&B ingests raw firmographic feeds daily from dozens of third-party data vendors. Before any Paydex score, Buydex signal, or corporate family tree can be trusted by an AI agent, the underlying business entity records must be cleaned, standardised, and resolved to a canonical DUNS number. Today this involves brittle stored procedures. Here is how dbt restructures it: STAGING LAYER (stg_vendor_records.sql): Each vendor feed gets its own staging model. The model casts raw strings to correct types, standardises country codes to ISO 3166, strips whitespace from business names, and renames columns to D&B's internal schema — all in a single SELECT. A not_null test on 'raw_duns_candidate' and a unique test on 'vendor_record_id' run nightly. INTERMEDIATE LAYER (int_entity_candidates.sql): A model joins staged vendor records to D&B's internal DUNS master table using blocking keys (country + postal code + name token). It outputs a candidate-match table — one row per (vendor_record, duns_candidate) pair — with a similarity score pre-computed via a dbt macro wrapping a warehouse-native fuzzy-match function. MARTS LAYER (mart_resolved_entities.sql): Applies a threshold rule (score ≥ 0.85 → resolved; < 0.85 → queued for human review). Materialised as a table refreshed daily. An accepted_values test asserts resolution_status is always one of ['resolved', 'pending_review', 'unresolvable']. SNAPSHOT (snap_duns_master.sql): A dbt snapshot captures SCD Type 2 history on the DUNS master table — so when a company's legal name or corporate parent changes, the old row is closed with a valid_to timestamp and a new row opens. This is the temporal audit trail that makes D&B's Ground Truth explainability story credible: an AI agent can always ask 'what did we know about this entity on date X?' and get a deterministic answer. METRICS LAYER: A dbt metric named 'entity_resolution_rate' is defined as resolved_count / total_candidate_count, scoped by vendor and date. Every BI tool — Tableau, Looker, the internal AI agent dashboard — queries this single definition, eliminating the 'which number is right?' argument in sales reviews. BUSINESS IMPACT: The entire pipeline is version-controlled in Git. A new vendor onboards by adding one staging model and one YAML test file — no stored procedure changes, no DBA ticket. The lineage graph in dbt docs shows exactly which raw vendor feed flows into which Paydex input feature, satisfying both internal audit and enterprise customer due-diligence requests.
