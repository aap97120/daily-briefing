🧠 Data Science Topic of the Day

🎓 Knowledge Graphs

Turning isolated facts into connected intelligence — the structural backbone of entity resolution at scale.

What It Is

A knowledge graph is a network of real-world entities (companies, people, products, locations) and the typed relationships between them, stored as triples: (Subject → Relationship → Object). Unlike flat tables or document stores, a knowledge graph makes relationships first-class citizens of the data model. Every node is an entity; every edge encodes meaning. The result is a queryable, traversable map of your domain. Neo4j, Amazon Neptune, and Google's Knowledge Graph are canonical implementations. In the B2B data world, a knowledge graph is how you answer questions like 'Which of my prospects are subsidiaries of a company already in legal dispute with one of my top customers?' — a query that would require five brittle SQL joins but is a single graph traversal.

How It Works

1. ENTITY EXTRACTION: Named Entity Recognition (NER) pulls entities from raw text, firmographic feeds, filings, and web crawls — companies, people, addresses, SIC codes, UBOs. 2. TRIPLE CONSTRUCTION: Each fact becomes a subject-predicate-object triple. Example: (Acme Corp) —[SUBSIDIARY_OF]→ (GlobalCo Inc). Triples are stored in a graph database or RDF triplestore. 3. ONTOLOGY / SCHEMA: A formal schema (ontology) defines allowed entity types and relationship types. This enforces semantic consistency — 'acquired' means the same thing everywhere in the graph. 4. ENTITY RESOLUTION: Deduplication links multiple representations of the same real-world entity (Acme Corp, ACME Corporation, Acme Corp Ltd) to a single canonical node — this is exactly what DUNS numbers do. 5. INFERENCE & REASONING: Graph traversal algorithms (BFS, DFS, PageRank, shortest path) reveal implicit relationships. Ontological inference can derive new facts: if A owns B and B owns C, infer A controls C. 6. EMBEDDING (OPTIONAL): Techniques like TransE, RotatE, or Graph Neural Networks (GNNs) project nodes and edges into dense vector space, enabling ML tasks like link prediction ('which companies are likely to merge?') and node classification. 7. QUERY LAYER: SPARQL (RDF graphs) or Cypher (Neo4j) let analysts and agents traverse the graph with expressive, path-aware queries that flat SQL cannot replicate efficiently.

When To Use

USE IT WHEN: (1) Relationships between entities are as important as the entities themselves — corporate hierarchies, supplier chains, beneficial ownership. (2) You need multi-hop reasoning: 'customers of my customers,' 'competitors of my prospects' subsidiaries.' (3) Entity resolution is a core problem — merging fragmented records into a unified, deduplicated view. (4) Your domain has complex, evolving schemas that would be brittle in a relational model. (5) You are building agentic AI systems that need structured, navigable world-knowledge as a reasoning substrate rather than pure vector retrieval. AVOID WHEN: Your data is truly tabular with no meaningful entity relationships, or query patterns are simple aggregations that OLAP handles cheaply. Graph databases are operationally heavier than Postgres for simple workloads.

🎯 Worked Example — D&B Context

D&B's 600M+ business record corpus is, at its heart, a knowledge graph problem. Consider the Pipeline Risk & Revenue Protection agent archetype. A sales rep's $2M deal is with Apex Manufacturing — but the agent needs to know if Apex is financially stressed. In a flat data model, you query Apex's Paydex score directly. In a knowledge graph, the agent traverses: (Apex Manufacturing) —[SUBSIDIARY_OF]→ (Titan Group Holdings) —[HAS_LEGAL_FILING]→ (Chapter 11 Petition, Filed July 2026) AND (Titan Group Holdings) —[ULTIMATE_BENEFICIAL_OWNER]→ (Viktor Sorokin) —[SANCTIONED_BY]→ (OFAC List, August 2026). The flat query misses the risk entirely; the graph traversal surfaces it in one hop. Now extend this to the Prospecting agent: traverse D&B's corporate family tree graph to find all US subsidiaries of European parent companies with Paydex > 80 AND headcount growth > 15% YoY AND no existing D&B contract — that is a high-precision ICP filter that reads naturally as a graph query (MATCH path in Neo4j Cypher or a LangGraph tool call against a Neptune endpoint). This is also why DUNS as a universal node identifier is so powerful — it is the primary key of the entire knowledge graph, making D&B the canonical entity resolution layer any agentic workflow must pass through.
